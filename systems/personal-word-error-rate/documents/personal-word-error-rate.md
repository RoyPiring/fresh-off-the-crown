## Measuring My Own Word Error Rate

### Why personal measurement matters

I measured the Word Error Rate of the Antigravity CLI transcription system using my own voice, vocabulary, microphone, and acoustic environment. The build compared a sealed reference passage with the raw transcript produced from one spoken reading. This gave me a personal accuracy result instead of relying only on a published benchmark.

Standard benchmarks do not represent every real use case. My passage contained terms such as NextWork and jiwer, which differ from common clean-speech test material. My microphone and room conditions also affected what the model received.

The personal test showed how the transcription system handled the words I use under the conditions I work in. It did not replace the published benchmark. It added a local measurement that I could inspect through the total WER and the substitutions, insertions, and deletions behind that rate.

### Building the scoring script

I wrote a Python scoring script with the jiwer library to compare the reference passage with the transcript generated by the Antigravity CLI. The script calculated Word Error Rate and aligned both texts at the word level. This turned the transcription result into a measurable error rate instead of a judgment based on how the transcript looked.

The alignment separated errors into substitutions, insertions, and deletions. A substitution meant the model returned the wrong word. An insertion meant it added a word that was not in the reference. A deletion meant a reference word was missing from the transcript.

Using a script made the comparison repeatable. I could score the jargon passage, the plain passage, and later recordings through the same calculation. The result still depended on clean file handling because the script had to receive the intended reference and raw hypothesis files.

![Image](https://nextwork.ai/refreshed_maroon_timid_jujube/uploads/9aa05812-3049-449d-93bb-ad65f8e734d6_0p41pq9v)

### Reading the word-level alignment

I saved predictions.txt before scoring the recording, and all three predictions had observations. The first prediction was correct: no separate API key was needed because /voice used the Google account already signed in. The second prediction was not correct because recording started immediately and the microphone worked on the first attempt.

My third prediction estimated an 8.5% WER. The measured result was 16.5%, which was 8.0 percentage points higher than I expected. It was also above the published 4.0% benchmark used for comparison.

The word-level alignment explained how that result formed instead of leaving 16.5% as an isolated number. It showed which reference words were replaced, added, or omitted. This mattered because two recordings can have similar WER values while failing in different ways. The alignment made the error pattern available for review.

## Setting Up the Tools

### Why these tools come first

I created a dedicated folder and wrote a reference passage containing technical jargon before recording any audio. The folder kept the reference, predictions, transcripts, and scoring files together so the Python script could find the correct inputs. This reduced the risk of comparing the wrong files or mixing results from separate runs.

The reference passage established the exact words the recording was meant to contain. Its domain terms made the test reflect my vocabulary rather than a generic speech sample. Preparing it first also prevented me from changing the expected text after seeing the transcript.

The environment needed to support both transcription and scoring. Antigravity CLI captured the spoken passage, while Python and jiwer measured the difference between the saved reference and raw output. Setting up those parts first created a controlled path from spoken input to a scored and reviewable result.

![Image](https://nextwork.ai/refreshed_maroon_timid_jujube/uploads/9aa05812-3049-449d-93bb-ad65f8e734d6_qrvvg7eg)

### What each tool does

Antigravity CLI, called with agy, was Google’s terminal agent used to reach the transcription service after sign-in. The /voice command started the recording path and returned the speech-to-text output. No separate API key was required during this run because the CLI used the Google account already signed in.

Python 3.13 ran the scoring script. It loaded the sealed reference and raw hypothesis files, passed their contents into the scoring logic, and printed the calculated Word Error Rate.

The jiwer library handled the word-level comparison. It aligned the reference with the transcript and counted substitutions, insertions, and deletions. Those counts produced the WER and showed how the transcript differed from the intended passage. Together, the three tools covered capture, processing, calculation, and inspection without requiring a manual accuracy estimate.

## Sealing the Reference and Writing Predictions

### Why the reference must be sealed first

I created the jargon reference passage and saved it before recording the spoken version. I also recorded three predictions in separate text files before testing the Antigravity CLI. This established the expected words and my assumptions before any transcript or score could influence them.

Sealing the reference protected the ground truth. If I changed the passage after seeing the model output, I could make errors disappear by rewriting the expected text to match the transcript. The resulting WER would then measure my corrections rather than the transcription system.

Writing the predictions first served the same purpose. It allowed me to compare what I expected with what the tools produced. The final record showed which predictions matched, which failed, and how far the measured 16.5% WER differed from my 8.5% estimate. This kept the exercise based on recorded evidence instead of hindsight.

### My WER prediction and reasoning

I predicted an 8.5% Word Error Rate before recording the passage. I expected the score to be higher than the published 4.0% benchmark because that number represented typical clean speech rather than a guarantee for my voice, passage, microphone, or room.

The reference included technical terms such as NextWork and jiwer. These words were important to my use case, but they were also terms a speech model could miss, replace, or omit. That made a personal rate more useful than assuming the published result would transfer directly to my recording.

The measured WER was 16.5%, which exceeded my prediction by 8.0 percentage points and the published benchmark by 12.5 percentage points. The difference showed that my initial estimate was too low for this run. It did not identify one cause by itself, so the alignment and later comparison were needed to examine the error pattern.

I tested Antigravity CLI dictation without adding an API key or completing extra API configuration first. The purpose was to observe the default behavior of /voice under the account and environment already available. This let me test the setup requirement before changing anything that could affect the result.

The cold run checked whether the command would start recording, whether the microphone would work, and whether authentication through the signed-in Google account was enough. I had recorded predictions for these conditions before opening the voice path.

This test separated tool access from transcription accuracy. A failed setup would have prevented the passage test, while a successful setup allowed me to continue without adding another credential. The cold result therefore established the starting condition for the later recording. It did not measure WER by itself, but it confirmed that the transcription path was ready to capture the reference passage.

## Recording the Passage Once

### One unrehearsed reading, no retakes

I read the sealed reference passage aloud once without rehearsing it or recording another take. The Antigravity CLI captured that single reading and produced the transcript used for the first WER calculation. This preserved the normal speaking errors, pauses, and capture conditions present during the initial attempt.

Allowing retakes could have lowered the score through practice. I could change my pace, pronunciation, or distance from the microphone after learning which words caused trouble. That would measure a revised performance rather than the first cold reading.

The one-take rule kept the test tied to the original conditions. It did not prove that 16.5% represented every future recording because another reading could produce a different result. It provided one controlled sample that could be compared with the sealed reference, the 8.5% prediction, the published 4.0% benchmark, and the later plain-language recording.

![Image](https://nextwork.ai/refreshed_maroon_timid_jujube/uploads/9aa05812-3049-449d-93bb-ad65f8e734d6_uvm6o3d7)

### Keeping the measurement uncontaminated

I saved the raw model output in hypothesis.txt and did not correct its spelling, punctuation, or word order. The file remained the direct transcript produced by the Antigravity CLI. This preserved the evidence used by the scoring script.

Editing hypothesis.txt before scoring would have changed the system being measured. Any correction I made could remove a substitution, insertion, or deletion and lower the reported WER. The result would then describe the transcript after human repair rather than the transcription model’s original output.

Keeping the hypothesis untouched also made the comparison repeatable. The same reference and hypothesis files could be scored again with the same script and inspected through the same word-level alignment. This created a clear boundary between model output and human review. I could discuss the errors after scoring them, but I did not rewrite the input to produce a better result.

## Proving the Measurement Is Sensitive

![Image](https://nextwork.ai/refreshed_maroon_timid_jujube/uploads/9aa05812-3049-449d-93bb-ad65f8e734d6_bnx1011s)

### Jargon vs. plain passage: what the rate reveals

The plain passage produced a 15.4% WER. That was slightly lower than the first jargon result of 16.5% and clearly lower than the second jargon result of 24.2%. The 1.1 percentage-point gap between the plain passage and first jargon take showed only weak sensitivity to jargon in that comparison.

The 7.7 percentage-point increase from the first to the second jargon take showed stronger sensitivity to how the recording was captured. The passage type alone did not explain the full change because two takes involving jargon produced different rates.

All three runs were deletion-heavy. That pattern meant missing text had a large effect on the scores. Wrapping or OCR clipping could therefore move WER as much as word choice did. The comparison showed that the measurement responded to changed inputs, but it also limited the conclusion: this evidence did not support blaming the higher rates only on technical vocabulary.

## Reflections and Takeaways

### Key tools and concepts

I used the Antigravity CLI for speech-to-text transcription, Python 3.13 to run the scoring process, and jiwer to calculate Word Error Rate and align the texts. These tools created a path from one spoken reading to a numerical score and a word-level error record.

The main lesson was that speech accuracy should be measured under the conditions where the system will be used. A published benchmark did not account for my voice, microphone, room, or terms such as NextWork and jiwer. Sealing the reference before recording also protected the ground truth from later edits.

Comparing jargon and plain passages showed how carefully WER must be interpreted. The first gap between them was small, while the second jargon take rose sharply. Because every run was deletion-heavy, capture behavior such as wrapping or OCR clipping could affect the rate alongside vocabulary.

### Time and challenges

This build took approximately 30 minutes. The hardest part was keeping the file names and locations exact so the scoring script could find and compare the intended jargon and plain-text passages. A correct formula would still produce the wrong result or fail if it loaded the wrong reference or hypothesis.

The process included several files with different roles. The reference stored the sealed ground truth, hypothesis.txt stored the untouched model output, and predictions.txt preserved my expectations before scoring. The plain and jargon comparisons also had to remain separate.

Careful placement protected the evidence chain from recording through calculation. Once the script received the correct files, jiwer could align the words and report substitutions, insertions, deletions, and total WER. The challenge showed that measurement quality depends on input control as much as the scoring code.

### What's next

I completed this build to learn how to measure my own Word Error Rate and compare it with an industry benchmark using Antigravity CLI, Python, and jiwer. The result gave me a 16.5% WER for the first jargon recording, compared with my 8.5% prediction and the published 4.0% benchmark.

The plain and jargon tests also showed that vocabulary was not the only source of variation. The plain passage scored 15.4%, while the second jargon take reached 24.2%. Deletion-heavy output pointed to capture conditions, wrapping, or OCR clipping as factors that could affect the score.

My next step is to learn how speech-to-text models can be fine-tuned for domain-specific jargon. Any later change should be tested with the same sealed-reference method so the before-and-after results measure the system rather than edits to the benchmark.
